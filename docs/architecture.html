2. Data Model (versioned, append-only)

Every edit inserts a new row (db.*.insert_many([data])); reads take the latest via SELECT DISTINCT ON (key) … ORDER BY id DESC. History is implicit, nothing is ever updated in place. Wrappers force resort=False, reindex=False, restat=False (seminars/__init__.py:39-52).

2.1 Data volume (measured live 2026-11-11)

Via public POST /api/0/search/* with limit/offset probes + offset binary search:

CorpusCountAvg sanitized record
Public series (visibility=2)~2,359~0.8KB
Public talks (hidden=False, visible series)~47,938~1.1KB

Current public versions ≈ ~55MB over the wire. DB-side is larger: rows carry all search_cols, the schema is append-only (every edit = full new row, deleted rows retained), plus non-public rows, users, institutions, organizers, and the knowl DB. Estimate: low hundreds of MB (~200–600MB with indexes); compressed pg_dump likely ~100–300MB (their configfiles/backup.sh does pg_dump --format tar). Public corpus is harvestable (~25–50 paged requests); private data (emails, tokens, subscriptions) is not.

3. Key Request Flows

3.1 Edit seminar / talk (write path)

POST /create/save/seminar/  → create/main.py:435 save_seminar()
POST /create/save/talk/     → create/main.py:828 save_talk()
POST /create/save/schedule/ → create/main.py:1075 save_seminar_schedule()  (N unbatched inserts!)
POST /api/0/save/series|talk/ → api/main.py:340,462  (display=False gate + review queue)

Cost per save: 3–6 versioned reads (DISTINCT ON), up to 10 sequential users.lookup (organizers), talks_max() scan, email_validator. No index rebuild, no mail, no cache purge — writes are cheap; bulk schedule-save is N commits.

3.2 Read / browse / search

GET /                          homepage browse (bounded LIMIT 100+200 + pruned projection + TTL dict cache; fixed #217/#745 via fix-745-perf)
GET /search                    filtered talk search
GET /api/0/search/series|talks  machine API (operator/dict filters; #984/#986 500s → fixed by #987, integrated)
GET /api/0/lookup/series|talk   single-record fetch

3.3 Calendar export (ICS — on-demand, uncached)

GET /seminar/<short>/ics   homepage/main.py:941  (per-series, already filters ctr>0)
GET /talk/<id>/<ctr>/ics  homepage/main.py:956  (single talk)
GET /ics/<token>             users/main.py:617      (favorites → user.ics_talks; ctr<0 tombstones filtered by #989)

Generation: utils.py ics_file() + talk.py event() → DTSTAMP=edited_at (fallback start_time), stable UID {id}/{ctr}@topdomain, SEQUENCE:0 + LAST-MODIFIED, METHOD:PUBLISH, text/calendar inline, ETag/Last-Modified with 304 (fix-feed-hardening, PR #1012). Favorites query does a full all_seminars() scan + per-subscription $or + Python filter/sort (pwdmanager.py:466-484). External clients poll on their schedule (Google ~12–24h, Outlook 24h+, no SLA); Google drops feeds over ~1MB/~1111 events (#777 — documented #991, feeds now stable/small; pull-only by design).
